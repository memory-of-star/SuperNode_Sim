请使用我已有的仿真器，对 **Kimi K3 在 2、4、8 张 NPU 上的 TP 和 PP 推理性能**进行建模与对比实验。

先阅读仿真器实现、配置格式和相关说明，尽量复用已有能力；如果缺少必要能力，明确指出并做最小修改。所有结果应可复现，区分模型假设、仿真结果和仿真器暂不支持的部分。

需要完成三组同卡数对比：

- **TP2 vs PP2**
- **TP4 vs PP4**
- **TP8 vs PP8**

分别研究单请求 TPOT、多请求总吞吐、扩卡效率，以及计算、显存和通信瓶颈。

**1. 硬件参数**

| 参数 | 设定 |
|---|---|
| 单卡峰值算力 | **2.3 PFLOPS** |
| 算力利用率 | **90%** |
| 单卡有效算力 | **2.07 PFLOPS** |
| 单卡显存容量 | **1 TB** |
| 单卡峰值显存带宽 | **2.5 TB/s** |
| 显存带宽利用率 | **90%** |
| 单卡有效显存带宽 | **2.25 TB/s** |
| 单卡通信带宽 | **总共 128 GB/s，所有通信流共享** |
| 单跳链路固定延迟 | **2 μs** |
| 互联拓扑 | **Ring** |

容量和带宽采用十进制单位：GB = \(10^9\) bytes，TB = \(10^{12}\) bytes。FMA 按 2 FLOPs 计算。

将相关矩阵运算统一按上述有效算力建模，作为抽象 NPU 假设；不自行推定不同精度的硬件峰值。非矩阵算子如果需要其他性能参数，请列明假设。

90% 利用率只作用于计算和显存带宽，**通信带宽不再乘 90%**。如果仿真器已通过算子效率模型表达利用率，避免重复折损。

**不要沿用 2.3 TFLOPS、full mesh 或每对卡独享 128 GB/s 的旧假设。**

**2. 通信带宽口径与拓扑**

“每卡总共 128 GB/s”有收发口径歧义，因此做两组实验：

- **主实验：每卡发送与接收合计不超过 128 GB/s**，两个邻居方向共享预算。
- **对照实验：每卡总发送上限 128 GB/s，总接收上限独立为 128 GB/s**，两个邻居仍共享各自的预算。

不能给每条邻接链路或每个并发流重复分配完整的每卡带宽。

拓扑如下：

```text
2 卡：0 — 1

4 卡：0 — 1 — 2 — 3 — 0

8 卡：0 — 1 — 2 — 3 — 4 — 5 — 6 — 7 — 0
```

2 卡不因 ring 表示而自动获得两条独立物理链路。

非邻接卡通信必须经过 ring 路由，计入沿途链路与卡端资源占用。明确仿真器使用存储转发还是 cut-through，以及多跳延迟如何累计。

使用 **Kimi K3 原版混合精度权重**。优先读取模型配置、权重元数据或仿真器已有的模型描述。

参考参数：

| 项目 | 参数 |
|---|---:|
| 总参数 | 约 2.8T |
| 每 token 激活参数 | 约 104B |
| Decoder 层数 | 93 |
| Dense 层 / MoE 层 | 1 / 92 |
| KDA 层 / MLA 层 | 69 / 24 |
| Hidden dimension | 7168 |
| 路由专家 latent dimension | 3584 |
| 每层路由专家总数 | 896 |
| 每 token 选择专家数 | 16 |
| 共享专家数 | 2 |
| 专家 intermediate dimension | 3072 |

参考资料：

- [Kimi K3 模型说明](https://huggingface.co/moonshotai/Kimi-K3)
- [模型配置](https://huggingface.co/moonshotai/Kimi-K3/blob/main/config.json)
- [AMD 权重与 TP 分片分析](https://www.amd.com/en/developer/resources/technical-articles/2026/kimi-k3-on-amd-instinct-gpus.html)

建模要求：

- 区分 MXFP4 路由专家权重与其他高精度权重，计入量化 scale。
- 激活通信基准使用 BF16；需要其他精度时单独说明。
- **不能将全部 104B 激活参数都按 4 bit 计算。**
- **不能将整个约 1.56 TB checkpoint 当成每个 decode token 的读取量。**
- 计入 MLA 的 KV-cache 访问、KDA 状态更新和 AttnRes 状态。
- 权重常驻设备显存，不允许隐式 CPU、SSD 或其他卸载。
- 每卡容量核算包含权重、复制权重、KV/state、通信缓冲和工作区。
- 超容量配置标记为不可运行，不继续报告其正常性能。

公开的 TP8 分片资料只作为参考，不代表 TP2、TP4、TP8 必须采用相同的复制和切分策略。实际采用的策略必须记录。

**4. TP 执行模型**

对 TP2、TP4、TP8：

- 对支持切分的矩阵和注意力头进行张量并行。
- 明确哪些投影、路由器和其他权重需要复制，计入复制计算和显存访问。
- 记录通信操作类型、次数、消息大小和数据依赖。
- 主实验使用 **ring all-reduce：reduce-scatter + all-gather**。
- 2 μs 是单跳通信步骤延迟，不能直接作为整个 all-reduce 的延迟。
- 若支持实际可行的归约融合，可增加优化实验，保留未融合基线。

以下是未融合通信次数的量级参考，应以实际计算图为准：

| 通信位置 | 次数/token | 向量维度 |
|---|---:|---:|
| 注意力输出 | 93 | 7168 |
| 共享专家输出 | 92 | 7168 |
| 路由专家 latent 输出 | 92 | 3584 |
| 首层 dense 输出 | 1 | 7168 |

不要把这一参考清单机械套用到不同融合实现中。

**5. PP 执行模型**

对 PP2、PP4、PP8：

- 按连续层划分阶段，尽量均衡实际执行时间，而不只是均分层数。
- 报告每阶段层范围、权重容量、计算量和执行时间。
- 93 层不能整除 2、4、8；KDA、MLA 和 dense/MoE 层开销也不同，需要体现负载不均衡。
- 阶段间传输包括后续阶段所需的 hidden、残差和 AttnRes 状态，不能只算一个 hidden 向量。
- 保留同一请求的自回归依赖：末阶段完成并产生下一个 token 后，该请求才能进入下一轮。
- 多请求允许不同 microbatch 在不同阶段并行。
- 计入流水线气泡、排队、阶段不均衡和调度限制。
- 计入末阶段向首阶段返回生成 token 的通信；在上述 ring 中，末卡与首卡相邻。

**6. 通信模型校验公式**

令：

- \(N\)：TP 卡数；
- \(M\)：一次 all-reduce 中每个 rank 的完整输入张量大小，单位 bytes；
- \(\alpha=2\ \mu s\)；
- \(\beta=128\ \text{GB/s}\)。

Ring all-reduce 共 \(2(N-1)\) 个通信步骤。每卡发送量和接收量分别为：

\[
V_{\text{send}}=V_{\text{recv}}
=\frac{2(N-1)}{N}M
\]

无其他竞争时，主实验“收发合计 128 GB/s”的校验公式为：

\[
T_{\text{AR}}
\approx2(N-1)\alpha+
\frac{4(N-1)M}{N\beta}
\]

对照实验“发送、接收各自 128 GB/s，允许全双工”为：

\[
T_{\text{AR}}
\approx2(N-1)\alpha+
\frac{2(N-1)M}{N\beta}
\]

对应关系：

| TP 规模 | 固定延迟项 | 收发合计口径的传输项 | 收发独立口径的传输项 |
|---|---:|---:|---:|
| TP2 | 4 μs | \(2M/\beta\) | \(M/\beta\) |
| TP4 | 12 μs | \(3M/\beta\) | \(1.5M/\beta\) |
| TP8 | 28 μs | \(3.5M/\beta\) | \(1.75M/\beta\) |

这些用于校验量级。实际仿真应按通信步骤、链路与卡端资源推进。

通信与计算是否重叠，由执行图依赖和硬件资源决定，不要预设完全重叠或完全串行。

**7. 工作负载和实验矩阵**

主实验工作负载：

- 纯文本 decode。
- 初始上下文 **8192 tokens**。
- 每个请求生成 **256 tokens**。
- 不计 prefill 时间，但建立相应 KV/state。
- 随输出增长更新上下文长度，明确测量区间。
- 禁用投机解码、前缀缓存共享和卸载。

全部六种配置：

```text
TP2、PP2、TP4、PP4、TP8、PP8
```

每种配置测试全局并发：

```text
B = 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024
```

**B 表示整个实例的请求总数，不是每卡 batch。** 普通 decode 中，每个请求每轮生成一个 token。

- TP：允许将这些请求组成 decode batch。
- PP：对相同全局 B 测试不同 microbatch 划分。
- PP 划分满足：`microbatch 数 × 每个 microbatch 请求数 = B`。
- 测试单请求 microbatch 和较大 microbatch。
- 同时报告固定划分结果，以及支持范围内的最佳划分，并说明优化目标。
- 特别关注 PP2/PP4/PP8 在全局 B 小于、等于、大于阶段数时的气泡。
- 所有对比保持相同请求集合、上下文长度、输出长度和卡数。

超容量或仿真成本过高时可以停止扩展，但需记录原因。可补充 1K、32K 上下文敏感性实验，优先完成 8K 主实验。

**8. 批量 MoE 与显存访问**

不能直接将 batch=1 的权重访问量乘 B，作为所有 batch 的实际流量。

需要考虑：

- 不同 token 选择相同专家时的权重复用；
- 每个专家收到的 token 数和 GEMM 形状；
- 分块、缓存容量及权重重复读取；
- TP 切分对矩阵形状和访问模式的影响。

优先使用真实路由 trace。若没有，则使用固定随机种子的均匀 top-16、无放回采样，并明确属于合成路由假设。不同并行配置尽量使用同一请求的相同路由序列。

优先复用仿真器已有的 GEMM、缓存和分块模型，不能假定无限权重复用。

**9. 输出指标与报告**

提供可复现的配置、运行命令和 CSV/JSON 原始结果，至少包含：

| 指标 | 要求 |
|---|---|
| TPOT | 每请求平均值；有调度差异时报告 P50/P95 |
| 总吞吐 | 整个实例 output tokens/s |
| 每卡吞吐 | 总吞吐除以卡数 |
| 延迟加速比 | 同卡数 PP TPOT ÷ TP TPOT |
| 吞吐提升比 | 同卡数 TP 吞吐 ÷ PP 吞吐 |
| 计算与显存 | 活跃时间、利用率、访问字节数 |
| 通信 | 载荷时间、固定延迟、排队时间、每卡收发量 |
| PP 流水线 | 阶段利用率、气泡、最慢阶段 |
| 显存容量 | 各卡峰值占用、不可运行配置 |
| 瓶颈 | 计算、显存、通信带宽、通信延迟或调度 |

注意：

- 多请求场景不能用总吞吐的倒数代替每请求 TPOT。
- 因重叠而同时发生的开销，不应直接相加成端到端时间。
- 报告应区分资源忙碌时间与关键路径等待时间。

需要提供三类结果：

1. **同卡数比较：**TP2/PP2、TP4/PP4、TP8/PP8。
2. **固定全局 B 的扩卡比较：**TP2→TP4→TP8，PP2→PP4→PP8。
3. **配置优化比较：**相同全局 B 下，PP 不同 microbatch 划分的结果。

不要把增加请求数带来的吞吐变化误当成扩卡收益。

**10. 重点回答的问题与敏感性实验**

请明确回答：

1. B=1 时，TP2、TP4、TP8 相比同卡数 PP，分别降低多少 TPOT？
2. 随全局并发增大，TP 与 PP 的延迟、吞吐是否出现交叉点？
3. 每卡 128 GB/s 在哪些配置下成为显著约束？
4. “收发合计”和“收发独立”两种带宽口径对结果影响多大？
5. TP8 的计算和显存并行收益，是否抵消更多 ring 通信步骤的开销？
6. PP8 在什么并发、阶段划分和 microbatch 划分下能有效填满流水线？
7. 从 2 卡扩到 4 卡、8 卡，延迟收益和每卡吞吐如何变化？

在代表性配置上增加：

- **通信带宽翻倍，延迟保持 2 μs；**
- **通信延迟降至 1 μs，带宽保持不变。**

以性能改善幅度区分带宽瓶颈和延迟瓶颈，不能仅凭通信占比较高就认定带宽不足。

**11. 建模精度要求**

不要直接以“总 FLOPs ÷ 总算力”作为最终 TPOT，也不要用一个全模型的 `max(计算时间, 显存时间)` 替代执行图。

优先按算子、数据依赖、链路、显存和计算资源约束仿真。对仿真器无法表达的行为，应列明简化方式、可能偏差方向及结果适用范围。
