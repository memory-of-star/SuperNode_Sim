# topology.md 与 SUE Scale-Up Ethernet 仿真平台 v2 的适配评估

> 后续进展：v2 已完成适配与96项模型窗口实验，见 [v2报告](simai-scaleup-main/reports/v2-topology-kimi-glm53/report.html)。后续逐包测试另发现端口VRF配置缓存只有256项，v2已扩至1024项；因此下面关于动态端口容器的静态判断不能等同于原版576口VRF已可用。以下保留实施前的评估。

## 结论

**可以在当前 SUE 底座上扩展支持这组拓扑，但当前 AI harness 不能直接输入并完整运行它们。** 底座已有多端口、Die 编址、VRF 分表、200G 链路和 SUE 的 LLR/CBFC；其中 **8 XPU、单交换机、8 VRF** 已有高度对应的专用测试程序。缺口主要在拓扑入口、端口组选路、UCIe 环、接收侧代答与响应原路返回，以及大规模编址和验证。

这里的“支持”分为三个层次：

1. **结构可表达**：能创建端口、链路和转发域，并生成符合公式的路由。
2. **行为可仿真**：实际报文遵循端口组哈希、跨 Die 转交、代答和回程约束。
3. **性能可信**：相关带宽、缓冲、处理时延、竞争与硬件参数经过校准。

目前第一层已有大部分基础；第二层尚不完整，尤其涉及 UCIe 的档位；第三层不能仅凭拓扑连通性检查认定成立。无需为了接入这些拓扑更换 SUE 的 LLR/CBFC 协议。

原始方案完整保存在 [topology.md](topology.md)，本次没有修改其中的公式、判断或措辞，也没有修改仿真器代码。

## 各档支持情况

下表中的“需适配”不是现成可运行配置，也不表示本次已经跑通逐包仿真。

| 文档档位 | 底座当前情况 | 完整运行所需工作 |
|---|---|---|
| 8 XPU / 1 SW / 8 VRF | 有对应专用程序 `sue-vrf-planes.cc`：4 Die×8 口、200G、按 Die 编址和按口号隔离 | 接入 DAG 工作负载；补软件选组、硬件组内哈希和 AXI 回程约束。现有测试直接按端口发流 |
| 16 / 32 / 64 XPU | 多端口和 VRF 路由原语可复用；没有这三个档位的 harness 模板 | 按公式生成交换机、端口与各 VRF 路由，扩展多端口收发与统计 |
| 6+8 / 8+8 / 32+32 | MPU 可先表示为 8 口通信端点；底座不要求每个 host 都是计算卡 | 增加 XPU/MPU 类型、共享 chip 编号、端口映射、组选择和通信任务；若要模拟内存服务，还需独立服务模型 |
| 128 XPU 奇偶分面 | 可表达 16 台交换机及同奇偶直接路径 | 跨奇偶 T2 还需目的侧 UCIe 转交与接收侧代答 |
| 128 XPU 分法轮转 | 可表达 A/B/C 分区和每 Die 对 2–3 条直接轨 | 必须模拟真实组内选口及静态代理 Die 选择，才能得到随选口变化的 T1/T2 分布 |
| 256 XPU | 可表达每个 `(Die,口号)` 一台交换机；既有 `chip*4+die` 编码到 1023 恰好用满 | 跨 Die T2/T3 还需 UCIe 环、转交和代答；大规模运行另需资源及性能验证 |
| 64+64 主方案 | 可表达 16 台交换机及 192/128 口的不对称接入 | 增加偶 Die 选组0、奇 Die 选组1的规则，验证坏组不可达；跨 Die 同样缺 UCIe/代答 |
| 64+64 内存池备选 | 可表达两个隔离内存池 | 明确半数 Die–MPU 及跨池 MPU–MPU 不可达，这是方案性质，不应由自动路由补通；跨 Die 转交仍需扩展 |
| 18 XPU / 16+8 / 144 XPU，576 口交换机 | 地址规模可容纳，交换机端口容器动态增长；未发现 `pCnt=256` 被用作 AddPort 硬上限 | 新增模板、576 口验证和规模压测；不能把 576 个可添加设备直接视为真实 115.2T ASIC 模型 |
| 576 XPU | 可表达 pure-rail 接线，但现有 Die 编码不能原样沿用 | 重新设计地址映射，加 UCIe/代答并验证 18,432 条链路；硬件 chip-id 限制需另行确认 |

## 源码依据与关键缺口

### 1. 已有 Die、32 口和 VRF，不是从零开始

[sue-vrf-planes.cc](simai-scaleup-main/ns-3-alibabacloud/simulation/scratch/sue-vrf-planes.cc) 定义了：

- 8 张卡，每卡 4 个 Die，每 Die 8 个端口。
- `XPU-ID = gpu*4 + die`，同一 Die 的 8 个口使用相同地址。
- 单交换机下，物理端口 `p=gpu*32+die*8+i`，入口映射 `VRF=i+1`。
- 每个 VRF 单独安装目的 Die 到同号出口的路由。
- 按端口、目的 Die 和 VRF 检查接收计数及 LLR 状态。

这与原文 §2.1 的接线和隔离结构一致，VRF 从1编号只是内部编号差异。它的 `SPLIT` 模式是 **8 张卡接 8 台各32口交换机**，不能误称为原文的“64张卡接8台256口交换机”。

[SUESwitchNode](simai-scaleup-main/ns-3-alibabacloud/simulation/src/sue/model/sue-switch-node.cc) 已有 `SetRoutingTable(vrf, rt)`；不存在的 VRF 路由表会 miss，不自动回退到 VRF0。VRF 可以由入口端口派生，不需要配置 IP 或依赖 VLAN 隔离。

但该底座实现的是 SUE AFH 的地址查表转发。能够复现文档的“按 SA、VRF 转发”行为，不等于已经实现真实设备完整的三层控制面。

### 2. 当前 AI harness 仍是单网口 host 模型

[harness/sue_harness.py](simai-scaleup-main/harness/sue_harness.py) 的拓扑类型只有 `single_switch` 和 `leaf_spine`，生成时每个 host 只有一条上联。

[sue-harness.cc](simai-scaleup-main/ns-3-alibabacloud/simulation/scratch/sue-harness.cc) 中 `Device(host)` 固定取设备0；收包回调也只挂在该设备。任务字段仅有主机级 `src/dst`，没有 `chip/die/port_group`。即使手工替换拓扑文件，多端口收发、地址归属和任务完成判定也不会自动适配。

任务中的 `vc=0..7` 是流控队列类别，**不是**8条轨，也不是8个 VRF。不能通过给任务换 VC 来模拟端口隔离。

现有 harness 使用 VLAN PCP 表达 VC。若严格遵循本方案“不带 VLAN”的帧格式，还需调整 VC 编码方式，例如使用底座已有的 shim 映射；入口端口仍可用于派生 VRF。

### 3. 端口组选路需要新增端点行为

现有交换机 ECMP 根据地址、FlowLabel 等做哈希，但这是交换机出口选择。文档要求的是**源 Die 只能选择一个4口组，再由硬件确定具体源口**，两者位置、候选集与故障行为均不同。

至少需要定义：选组策略、哈希键、种子、流内是否保持同口、链路故障后候选集是否变化。64+64 主方案选错组应按模型报告不可达，不能自动换组或从源侧换 Die 掩盖限制。

### 4. UCIe 环与接收侧代答尚未实现

[platform-capabilities.md](simai-scaleup-main/docs/platform-capabilities.md) 将 Die 间 D2D 接口列为建议、未实现的扩展。此次对 SUE 模型源码的检查没有发现本方案要求的四 Die 环及代答机制。

完整实现至少包括：

- 每张 XPU 内的双向环、方向带宽、处理/传播时延、队列及竞争。
- 指定报文先过交换机，再由目的卡代理 Die 转交目标 Die。
- 将“代理端收到”与“目标 Die 真正收到、任务可以完成”分开。
- 保存请求进入的端口及事务关联，使响应由代理 Die 从原口发出。
- 明确多种可选代理 Die 的静态选择规则，以及对角路径的方向选择。

DAG 中增加一个固定等待任务只能近似额外时延，无法产生 UCIe 带宽竞争或证明代答正确。底座另有 [sue-axi-workload.cc](simai-scaleup-main/ns-3-alibabacloud/simulation/scratch/sue-axi-workload.cc) 的读写事务及响应示例，但它是两个单端口端点的实验，不能作为这里多 Die、多口代答已实现的证据。

### 5. 576 口和 576 张卡是两个不同问题

交换机声明里虽然有 `pCnt=256`，实际 `AddPort` 使用 `vector` 并随端口数调整挂起队列；该常量在 SUE 源码中没有被用于拒绝第257口。因此不应据此断言底座“最多256口”。不过576口尚需专门验证，设备/队列可创建也不代表共享缓存、仲裁或交换容量已按目标 ASIC 建模。

[sue-header.cc](simai-scaleup-main/ns-3-alibabacloud/simulation/src/sue/model/sue-header.cc) 的 `SueMacFromXpuId` 和 `GetXpuId` 只编码/提取10位。沿用现有 `4*chip+die` 时：

- 144卡需要576个地址，能容纳。
- 256卡需要1024个地址，恰好到边界。
- 576卡需要2304个地址，原编码会截断并发生别名，不能直接使用。

这不是 ns-3 节点数上限，也不一定需要扩大 SUE 报头。576卡方案的每个域只含一种 Die，可以评估“10位字段承载 chip，Die 放在 MAC 其他位，并结合转发域解释”的编码；但必须新增一致的收发解析、SA唯一性及回程校验。另一条路是扩展查表键。两种都不是当前现成配置。

原文所述硬件 chip-id 最多支持512个，属于另一层约束；本次未验证该硬件规格，不能用软件能编号576卡替代硬件可部署证明。

## 本次结构验证

复现命令：

```bash
python3 topology-audit/check_topology.py
```

[检查脚本](topology-audit/check_topology.py) 根据文档映射公式构建16种拓扑，包括两种备选；[结果 JSON](topology-audit/results.json) 记录输入与脚本 SHA-256。

全部16种通过：端口范围、交换机容量、物理端口唯一性、链路数守恒、每 SA 每域至多一口、R1 隔离、R2 跨卡同 Die 同口号同域。R2 通过验证每个 `(Die,口号)` 在所有卡上的域完全相同来证明，不进行重复的二次方枚举。

同时计算了不同 Die 对的直接轨和整组覆盖、Die–MPU 及 MPU–MPU 路径数：

| 结构 | 六对不同 Die 的直接轨数 | 可锁定直接一跳的不同 Die 对 |
|---|---|---|
| 完整轨，含单台/多台归并轨 | 全部8条 | 6/6 |
| 奇偶分面 | 同奇偶8条，跨奇偶0条 | 2/6 |
| 分法轮转 | 按0-1、0-2、0-3、1-2、1-3、2-3顺序：3、3、2、2、3、3 | 0/6 |
| pure-rail | 全部0条 | 0/6 |

64+64主方案每 Die 到每 MPU 都有4条直接轨及1个完整可用组；内存池备选一半组合8条、另一半0条，且跨池 MPU 对为0条。

**这是独立的公式结构检查，不是 ns-3 逐包仿真。** 没有验证 UCIe、端口哈希概率、时延、吞吐、故障恢复或物理布线；也未复跑所有已有测试。原文提到的 `scaleup_topo/scaleup_viewer.html` 在此次工作区文件检索中未找到，因此不能声称复用了该查看器或核验了其全部图形。

## 原文中需要澄清的内容

以下保留在原文中，没有静默更正；实现时应以明确规则消除歧义。

| 位置 | 问题及建议口径 |
|---|---|
| §0 VRF唯一性 | “每 SA 每域至多1口”不等于“每张卡每域至多1口”。一张 XPU 有4个 SA，完整轨内通常占4口。应写“每个 Die/SA” |
| §0 链路编号 | `L=x*32+d*8+i` 只覆盖XPU链路；MPU还需补独立偏移，例如 `32*N_XPU+8*(m-N_XPU)+i`，前提是MPU编号紧接XPU |
| §1.4、附录A | “多台每台1个VRF，仅8+8例外”遗漏16卡每台4域、32卡每台2域。“同号口必同台”也不适用于拆轨后的任意不同 Die；R2限定同 Die 才成立 |
| §1.6 | 组内4口不应“全部属于同一个转发域”，那会违反R1。正确判据是每个候选源口所属的域中都有目的SA的对应口；四个域可以各不相同 |
| §2.2、§2.3 | 守恒应为 `8域×64口=512`、`8域×128口=1024`；不能再乘交换机台数。也可写 `2台×4域×64口`、`4台×2域×128口`。R1还依赖台内VRF，不能只称物理隔离 |
| §2.4、§2.5、§3.1、§3.4、§4.2、§4.3等带宽口径 | 可达口对数不能直接加成同时可用带宽。128个可达口对不代表25.6T：一张XPU只有32个200G口，单向上限6.4T。同样，单片MPU只有8口，单向上限1.6T；64+64主方案单个XPU–MPU对的16个可达口对也不能直接当作3.2T可同时吞吐。实际吞吐还受目的端共享、组选路、UCIe等限制 |
| §3.2 | 8+8的公式 `p=v*40+4x+d` 对应XPU占用0–31、40–71、80–111、120–151，而不是连续0–127；MPU插在各域尾部。公式本身端口不冲突 |
| §3.4 容错 | 单台故障会使所涉Die的R2路径从8条降为7条，因此“R2业务不受影响”不准确。仍有路径和仍保持完整8轨是两回事；组内哈希能否避开故障口还需故障选路策略 |
| §1.7、§5.2 | UCIe跳数由实际代理Die到目的Die决定，不总是源Die到目的Die的环距。轮转方案同一Die对可能因选口走T1或T2，因此不能统称三个方案的档位都不随哈希变化 |
| §3.3 最少8台 | 该结论需保留“每台一个VRF、每条完整轨不能跨台”等设计条件，不能将它推广为单由R1得到的所有拓扑下限 |
| §4.3、§4.4 扩容 | 144→288卡、576→1152卡不能只增加同规格交换机就宣称结构和档位全部不变。前者要拆轨、重新评估跨Die；后者同Die同口号已有1152个端口，超过576口，在无ISL下不能继续保证全网R2一跳 |

关于 OSFP/400G 面板、1拆2/1拆4以及 Die 分面：逻辑公式允许每条200G链路独立布线，而文档的部署限制明确指出连接器内端口号和分支上的Die归属未必可控。必须取得实际 lane→Die→port 映射，才能判断这些逻辑拓扑能否布成。Gearbox、外部PHY带来的延迟和带宽约束也需要另外输入；本次没有核验产品时间表或厂商规格。

## 推荐适配顺序

1. 复用现有8卡VRF程序的编址和路由方法，给 harness 增加 `chip/die/port/group`、MPU类型和16种公式生成器；先接通8/16/32/64卡及小规模混合档的DAG工作负载。
2. 增加源端组选路、按域静态路由和原口返回校验，验证R1/R2/R5；不要沿用自动BFS生成的跨平面ECMP表。现有VRF测试本身也在建网后覆盖自动路由。
3. 增加目的侧UCIe环、代理Die选择和代答完成语义，再运行128/256/64+64的T2/T3场景。
4. 验证576口设备规模，解决576卡编址与硬件约束，最后做大规模性能实验。

这一路径可以继续使用当前 SUE 链路协议，把新增工作集中在拓扑、端点和 Die 内通信模型上。
