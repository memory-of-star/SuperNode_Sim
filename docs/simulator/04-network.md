# 4. SUE网络、拓扑、路由、LLR、CBFC与时序

## 4.1 物理对象与包的组成

每个XPU有4Die×8个端口，每个MPU有8个端口；每条接入链路都创建host侧SueNetDevice、switch侧SueNetDevice和SueChannel。两端使用相同的该链路速率，XPU链路和MPU链路可以不同。设备使用SUE出口队列、信用流控和LLR引擎，而不是给消息直接添加一个固定网络等待时间。

应用载荷加入SueHeader和shim，以及仿真用PacketTag。Tag保存任务ID、分片号、载荷字节数和响应标记，不应把仿真Tag的C++对象大小当成真实线上协议开销。SA编码在MAC字段中，对应chip/Die；当前不为XPU和MPU配置IP，也不使用VLAN来代替VRF。

AFH（AI Fabric Header，当前使用Gen1 Lite转发）通过SUE头中的目的节点标识和转发域选择出口。准确的字段编码以项目`DESIGN.md`、`sue-header.*`和`SaMac()`为准；它不是IP路由或RDMA QP模型。

## 4.2 拓扑与转发域

基本一跳判定为`(switch, VRF)`相同。两个端口物理上在同一台交换机但VRF不同，仍然不通。相同SA的不同口需要保持隔离。适配器将面板物理端口号保存在CSV中，仿真内部设备号使用已接入端口的连续编号，两种号码不能混用。

| 家族 | 名称 | 主要特点 |
|---|---|---|
| 小规模完整轨 | xpu8 / xpu16 / xpu32 / xpu64 | 8条轨通过多VRF或不同交换机隔离 |
| 128卡拆轨 | xpu128-parity / xpu128-rotate | 奇偶分面或逐轨轮换2+2分组 |
| 单Die轨 | xpu256 | 每台对应(Die,口号)，跨Die需要目的侧环转交 |
| 混合 | mixed6-8 / mixed8-8 / mixed32-32 | XPU与MPU同域直通 |
| 大混合 | mixed64-64 / mixed64-64-pool | 好口成组或两个内存池的约束 |
| 576端口 | xpu18 / mixed16-8 / xpu144 / xpu576 | 大radix映射与拆轨 |
| 资源实验 | hw-N-M | N=4/8/16/32、M=0/2/4/8，固定8台256口交换机 |

`hw-N-M`为控制变量而保持八个物理轨，不与“8XPU单交换机满配”的原拓扑混为一谈。资源入口中的芯片数变化，没有自动套用原文各档最少交换机方案。

建图前检查端口守恒、交换机容量、物理端口唯一性、同SA每域最多一个端口、R1/R2以及10bit路由键碰撞。拓扑能创建与某个流量可达是两件事：错误端口组、跨隔离池等任务可以被记录为不可达负例。

## 4.3 端口组选路与任务哈希

每Die端口0–3为组0、4–7为组1。软件可以选择组，组内具体口通过哈希决定。默认`group=-1`时，Python和C++都先寻找四个口全部可达的组，再由哈希在可用组间选择；没有这样的组时仍选一个组，不能凭空使不可达目的变得可达。

哈希输入包含seed、task ID、源chip/Die和目的chip/Die。消息的所有分片固定使用同一个端口。多Die发送并不自动把每条消息再条带化到该Die的8个端口。不同任务才能通过哈希分散，流量小或任务少时一些口可能空闲。

同seed只保证在相同任务集合和编号下确定性；改变分片任务、插入远端读或改变布局会改变task ID，因此不能保证所有对照实验物理端口落点完全相同。

## 4.4 目的侧绕行与原口确认

直接同域可达时，目的Die自己接收。否则，只对XPU↔XPU寻找目的芯片上与源端口同域的代理Die，并在候选里选距离目标Die环跳数最小的一个，同距按Die编号稳定选择。MPU不提供这种跨Die兜底。

```text
源Die的固定口 → 一台交换机 → 目的代理Die的同号口
                                      ↓ UCIe环
                                   最终目的Die
                                      ↓ 64B完成响应的环返回
                                  代理Die原入口
                                      ↓ SUE
                                  源Die原出口
```

源侧不先绕到另一Die再上交换机。一个消息必须所有载荷片到达最终目的Die，才触发64byte适配器完成响应；源收到该响应后任务才完成。此响应与LLR的链路ACK不是同一层概念。

## 4.5 本地UCIe环

结构是0↔1↔2↔3↔0。相邻1跳、对角2跳，最短路径同距时固定选择顺时针。每芯片8条有向边各有下一可用时间；传输时间为排队＋`bytes×8/bitrate`＋每跳固定延迟。对角传输按两跳依次执行，消耗两条边。

每芯片共享有限容量池。一个片从准入到最后一跳到达一直占用池空间；池满时按照重试间隔等待。目的侧SUE进入环的片只有获得池准入后才归还对应信用，从而让环拥塞反压到网络接收路径。不是把整条UCIe环简化成一个不争用的固定延迟。

同芯片本地通信直接调用相同RingTransfer，不经过交换机；每个本地任务也分片。纯资源等待任务的`bytes=0`，本地环任务的真实字节数在resources侧车中，不能只加总tasks中的bytes来估计全部通信量。

## 4.6 LLR：逐链路可靠性

原协议实现的发送状态包括OFF、INIT、ADVANCE、REPLAY、FLUSH。正常可靠发送为帧分配序列号并保存重放副本；收到ACK后释放可回收项，NACK/定时器等触发重传，重试限制及同步异常可能进入FLUSH/重新同步流程。回放帧仍占用实际链路时间和缓冲，不是简单把时延乘上“错误率系数”。

本harness创建的设备启用LLR。`bad_every`非零时可对特定入口的数据帧做确定性注错以验证回放；它不是按真实PHY BER逐bit独立采样，也没有FEC纠错模型。未开启注错时也不能把所有系统抖动归因于LLR，队列与信用等待通常更直接。

LLR在每条链路上工作；应用任务的64B完成响应仍然需要完整传过网络。`replay_frames`表示重放计数，`discard`非零会使当前成功判据失败。更详细状态机与定时器遵循`src/sue/model/sue-llr-engine.*`及工程设计文档。

## 4.7 CBFC：逐VC信用流控

每个VC维护信用上限与消费/释放计数。概念上：

```text
CU = 已消费信用CC − 已释放信用CF（按实现的模计数规则）
允许发送 ⇔ CU + 本帧所需信用 ≤ 信用上限CL
```

帧按信用粒度折算，至少占一个信用；实现支持发送/接收粒度及CF_Update、CC_Update等控制机制。接收端腾出空间后反馈信用，发端更新后才继续。信用不足不会直接产生成功发送，而是阻塞/等待；链路控制帧、重放与应用数据共享实际时序约束。

`credits=512`不是512byte，也不是“队列长度512个任务”。当前检查按256byte信用粒度为最大分片预留额度，实际协议帧头和各类缓冲还需单独理解。

交换机出口拥塞、主机出口队列和目的侧环池可能通过信用/反压耦合。CBFC避免缓冲无界增长，但不意味着无限吞吐、没有头阻塞或所有构造都不会发生等待。

## 4.8 交换机、序列化与延迟抖动

SueNetDevice控制出队、线速发送、帧间隔及流控；SueChannel安排传播事件；SUESwitchNode在收到帧后进行VRF/路由查找、转发预算延迟和出口排队。当前不是交换ASIC内部每一级pipeline、共享buffer bank或真实crossbar调度的周期级模拟。

默认传播20ns和转发预算300ns是常量。观察到的不同任务时延仍可由以下因素产生：不同哈希落点、消息长度、队列积压、信用反馈、UCIe边竞争、资源FIFO、DAG通知、错误重放。**这是争用和路径导致的时延变化，不是已经加入了随机PHY jitter分布**。

想研究随机延迟分布、突发错误相关性或真实交换机调度，必须新增相应行为模型并校准参数；不能仅换seed就称模拟了所有真实噪声。

## 4.9 调度器和时钟

当前多Die入口使用单次仿真单线程，事件按ns-3规则推进。`ScheduleWithContext`保持事件对应的host上下文，模型中的皮秒统计与纳秒输入相互换算：1ns=1000ps，1µs=10^6ps。

外层同时跑3个case只意味着3个进程，不会使一个case拥有3倍链路或算力。相同条件的墙钟耗时可因CPU负载变化，仿真任务时间戳应保持确定；验证时比较仿真统计，不比较程序运行秒数。
