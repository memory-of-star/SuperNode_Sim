# CBFC CreditSize 异粒度设计 —— 双端 MMU cell 不一致的处理方案

> **状态**:已落地并全量验证(2026-08-31;TestSuite TS-62~65、场景 SC-36、scratch 回归 51 项 fail=0)。
> **规范依据**:UEC §5.2.5.8(非理想 CreditSize)、§5.2.8.2(链路级配置)、§5.2.10.1(CreditSize 支持集)、§5.2.5.6.4 / §5.2.5.7.4(CC_Update 对账)、§5.2.5.3(循环计数器安全区间)。
> **实现/评审基准**:DESIGN.md §12.56;测试见 `docs/test-cases.md` TS-62~65 / SC-36。
> 本文回答两个问题:**(1) 原始问题与我们的方案;(2) 反事实对比——设备 A 的 rx credit_size 也配成 32B 会怎样。**

---

## 1. 原始问题

直连两端的 MMU(缓存管理单元)cell 大小不一致:

| 设备 | MMU 原生 cell | 可配置性 |
|---|---|---|
| 设备 A(主机/NIC) | **128B**(使用率最高档) | 仅支持标准档位(2 的幂:32/64/128/256/512/1024/2048) |
| 交换机 SW | **56B** | 不可配(非标准值,ASIC 固定) |

**协议建议**(传统做法):同一条链路双向统一取 `min()` = 双方共同支持的最小值。本案 A 不支持 56,退到 32。

**min() 的代价**:
1. **SW 侧缓存记账失真**——SW 的 MMU 物理上按 56B cell 分配,信用账却按 32B 记,cell 计数被放大。实测(同字节在途量):min() 口径 432 cells vs 原生口径 252 cells,**放大 71%**;按 creditLimit×32B 反推的缓存预算与物理占用脱节。
2. **可能掉出线速**——SW 被迫以非原生粒度管理窗口,小帧场景下窗口利用率和吞吐受损(见 §3.4 a 臂与 d 臂的 cell 计数对比)。

**核心诉求**:同一个方向上,**cell_size 以接收端(RX)原生值为准**;发送端按对端 RX 原生值发送,但不支持时向下 snap 到自己支持的最大标准值。由此:A→SW 方向 A 发 32、SW 收 56;SW→A 方向 SW 发 128、A 收 128。

---

## 2. 标准依据(方案被 UEC 背书,但需补两条规则)

- **§5.2.8.2**:CreditSize 由**接收端** buffer 特性决定;`Sender.CreditSize ≤ Receiver.CreditSize`(尽可能接近),取双方共同支持值 → A 取 32 合规。
- **§5.2.10.1**:"要求所有实现支持任意 CreditSize 过于繁重"——合规最小集就是 2 的幂;56 只是推荐档,**保守方向(发送侧 ≤ 接收侧 cell)是硬性要求**。
- **§5.2.5.8** 直接给出异粒度的两种处理:**方法 1**(RX 收包立即返还多扣差值)与**方法 2**(RX 按原生 cell 记账,粒度差当"泄漏",由 CC_Update 周期对账回收)。本文采用**方法 2**——不动信用账本差分代数,改动集中在低频对账路径。
- **必须补的两条规则**(min() 直觉方案里容易漏):
  1. **TotalCredits = buffer_size ÷ 接收端 cell_size**(§5.2.8.2)。本案 A→SW 方向必须按 SW 的 56B cell 数设窗口,而不是 buffer÷32——否则 A 以为有 2.56× 的缓冲而超发。规范 5.2.5.8 的 8000B/80B-cell 算例:CreditSize 退到 64 后 TotalCredits 仍是 100 而不是 125。
  2. **发送端 PktOvhd ≥ 接收端实际 per-packet overhead**(§5.2.8.2 保守方向的伴随规则)。

---

## 3. 方案:每方向 RX 原生 cell + CC_Update 对账(方法 2)

### 3.1 规则

1. **每方向独立定 cell,以 RX 原生值为准**:A→SW 用 SW 的 56(SW 侧缓存按自己最优粒度记账,消除 min() 的缓存放大);SW→A 用 A 的 128。
2. **TX 端按对端 RX 原生值 snap-down**:A 理应用 56 但不支持,取支持集内最大 ≤56 的值 = 32;SW 发往 A 用 128(恰为标准值,无需 snap)。
3. **记账规则**:TX 每发 `ceil(F/tx_cell)` 记 CC;RX 每收/每 drain `ceil(F/rx_cell)` 记 R_CC/R_CF;**报文不足一个 cell 也占满一个信用**(保底 1)。
4. **泄漏与对账**:同方向 TX 与 RX 粒度不同时,`leak(F) = ceil(F/tx) − ceil(F/rx) ≥ 0`(tx ≤ rx 保证恒非负),逐帧从发送端 CU 泄漏;**周期 CC_Update 对账回收**:`LostCredits = S_CC − R_CC → 补进 R_CF,基线重置 R_CC := S_CC`。CU 呈锯齿(泄漏累积 → 对账清零),而非单调漂移。
5. **保序硬约束**(§5.2.5.6.4/§5.2.7.3):CC_Update 必须与数据帧在同一 MAC 队列严格按序——对账帧到达时它统计的所有包必已被收到,差值纯为粒度差,不含在途分量。本仿真由结构保证(控制帧只在帧间隙插发)。
6. **CU = CC − CF 差分代数与 mod 2^15/2^20 回卷零改动**——方法 2 的全部变化都在 CF 侧的绝对基线上。

### 3.2 走账示例(1518B 帧,PktOvhd=0)

| 步骤 | A 侧(÷32) | SW 侧(÷56) |
|---|---|---|
| A 发出 | S_CC += **48** | — |
| SW 收到 | — | R_CC += **28**(28 个 cell) |
| drain 完成,CF_Update | — | R_CF += 28 |
| A 收 CF_Update | S_CF := 28,**CU 挂着 20** | — |
| CC_Update 到达 SW | S_CC(48) 通告 | LostCredits = 48−28 = **20** → R_CF += 20 |
| 下一个 CF_Update | CU 回落 20,**账平** | — |

### 3.3 实现落点

| 位置 | 内容 |
|---|---|
| `SueCbfcEngine`(sue-cbfc-engine.h/.cc) | `m_txCellSize`/`m_rxCellSize` 双粒度;`PktCredits`(发送)/`RxPktCredits`(接收)分轨;`SetTxCellChoices` 支持集 + `AdoptTxCellFromPeerRx` snap-down;`OnCcUpdate` 对账公式零改动 |
| `SueNetDevice`(LLDP) | 广播值 = 本端 **rx 原生 cell**;采纳只写 tx、不碰 rx(修正旧代码整引擎覆写) |
| `SueConfig` | 新 GlobalValue `CBFC_TX_CELL_CHOICES`(CSV 支持集,模拟"仅支持 2 的幂");auto egress buffer 按 rx cell 计窗口 |
| 回归护栏 | rx==tx 时与旧单 cell 引擎**逐位一致**(TS-64);LLDP 采纳语义更新(TS-63 + sue-lldp-negotiate) |

### 3.4 仿真证据(四臂,100Gbps/1518B/窗口 4096 credits,SC-36)

| 臂 | 配置 | 吞吐 | 关键观测 |
|---|---|---|---|
| a | min() 32/32 | 100.36 Gbps(线速) | SW cell 峰值 432——记账放大 71% |
| b | **方案 32/56 + CC 10µs** | **100.31 Gbps(线速)** | CU 锯齿峰 2388,299 个 CC 帧,泄漏全额回收 |
| c | 32/56 无 CC(反例) | **硬停** | 仅 203 帧后 CU 卡死 4060/4096 |
| d | 理想 56/56 | 100.36 Gbps(线速) | SW cell 峰值 252(原生口径) |

**c 臂的教训比"掉速"更严重**:无对账时泄漏不可自愈——SW 排空后再无返还来源,交付量 ≈ `W / (1 − rx/tx)` 帧后永久停摆。这把"CC 周期必须满足 **dT ≤ W − BDP**"从理论变成定量证据。

## 4. 设计约束(随方案固化,防误用)

1. **CC 对账周期**:`dT ≤ W − BDP(按 tx cell 折算)`,否则泄漏在两次对账间吃满窗口(见 c 臂)。
2. **15 位 CF 循环计数器**:在途/未返还 credits 必须 **< 16384**(半模,§5.2.5.3)。`在途 ≈ RTT × 速率 ÷ tx_cell`。scale-up DAC(RTT≈1µs)安全;**长距互联前必须校核**。
3. **TotalCredits 按接收端 cell 计算**(§2 规则 1);**PktOvhd 取保守方向**(§2 规则 2)。
4. **保守方向硬规则**:`tx_cell ≤ rx_cell`。违反时 CU 低估在途、接收端缓存可能被超发,且首个 CC_Update 即报 LostCredits<0 严重错误(§5.2.5.7.4)。

## 5. 反事实对比:如果把 A 的 rx credit_size 也配成 32B

问题:方案里 A 是 `tx=32 / rx=128`;若 A 配成 `tx=32 / rx=32`(SW→A 方向也随之变为 32/32),会有什么影响?

先明确:**这对 SW 没有任何帮助**——SW 的缓存问题出在 SW 自己的 rx(保持 56 不变),由 A.tx snap 解决;A.rx 只影响 **SW→A 方向**和 **A 自己的接收路径**。影响取决于"A 的 32"是什么含义,分两种情形:

### 5.1 情形 a:A 的 MMU 真以 32B cell 运行(物理可配)

协议上自洽:SW→A 方向 32/32 同粒度,无泄漏、无需额外对账。代价全在 A 自己一侧:

| 影响 | 定量 |
|---|---|
| **15 位 CF 安全余量 ÷4** | 窗口上限 = 16384 credits × cell:32B 时 A 的信用窗缓存 ≤ **512KB**;128B 时 ≤ **2MB**。NIC 入口缓存普遍 1–2MB——32B 口径下**直接撞半模红线**,循环比较失去无歧义性(§5.2.5.3) |
| 20 位 CC 回卷快 4 倍 | 累计 32MB(32B)vs 128MB(128B)回卷一次;循环代数可处理,仅重同步点更密 |
| 记账密度 ×4 | 同字节在途的 credit 数 ×4,per-VC TotalCredits 数值 ×4,配置与对账算术压力增大 |
| 放弃 128 的选型理由 | A 选 128 是因为流量以大帧为主——per-cell 管理开销主导,cell 越小单位字节的管理状态越多。32B 只在小帧填充率上略有收益(64B 帧物理占 64B vs 128B),对 A 的流量结构是净损 |
| BDP 口径 | 400G × 1µs = 50KB 在途:32B → 1560 credits(9.5% 半模),128B → 390(2.4%);单独看都安全,**绑定约束是上面的窗口/缓存上限** |

### 5.2 情形 b:仅记账口径改 32,A 的物理 cell 仍是 128(危险)

这是**静默的安全洞**:信用协议只看"credits"抽象数,记账粒度(32)细于物理分配粒度(128)时,预留字节数 **少于** 物理占用:

| 帧长 F | 记账预留 ceil(F/32)×32 | 物理占用 ceil(F/128)×128 | 超订比 |
|---|---|---|---|
| 64B(以太最小帧) | 64B | 128B | **2.00×** |
| 65–96B | 96B | 128B | 1.33× |
| 97–128B | 128B | 128B | 1.00× |
| 1518B | 1536B | 1536B | 1.00× |

**64B 小帧洪峰下 A 的入口缓存可被超订至 2×**——无损契约(零 discard)在协议账本完全平衡的情况下被物理打破,且没有任何计数器能提前告警。这正是 §4 规则 4"接收端记账粒度 ≥ 物理 cell"的违反形态(§5.2.10.1 保守规则在接收侧的镜像)。

> 仿真边界说明:当前模型中 `SetRxCellSize(32)` 语义等于情形 a(记账与物理同粒);情形 b 的超订需要增加"物理 cell 占用追踪"才能在仿真里复现,列为后续工作。**结论不受影响**:情形 b 在实机上不可配置——接收端 rx cell 必须等于物理 cell。

### 5.3 结论

**A 的 rx 应保持 128(原生),不应配 32。**理由:

1. 对 SW 无益——方案对 SW 的收益全部来自"A.tx snap 到 32",与 A.rx 无关;
2. 情形 a 把 min() 的退化原样搬到 A 的接收侧(记账密度 ×4、CF 半模余量 ÷4、512KB 窗口上限),还给 SW→A 方向平添无谓的 4× credit 密度;
3. 情形 b 直接破坏缓冲安全(小帧 2× 超订,静默违约);
4. 方案的普适原则由此确立:**每个端口的 rx cell = 自己 MMU 的物理 cell(不可协商、不可妥协);tx cell = 对端 rx 原生值向自己支持集的 snap-down**。两端各自维护自己的最优记账,粒度差交给 CC_Update 对账——这正是"以 RX 为准"在两个方向上对称成立的原因。
