# MPU 文献综合与研究方向

整理日期：2026-11-03。配套 [资料索引](ref/README.md)、[来源与版本](ref/catalog.json)、[下载记录](ref/download-manifest.json)。本文是第一轮 31 项工作的综合分析；后续扩展为 42 项，最新判断见 [Scale-Up 专项核查](SCALEUP_MEMORY.md)，候选主线进一步转向读与分发融合。本文没有新实验结果，也不是已证明的新颖性声明。

**推荐收窄为：当远程内存访问与集合通信共享以太网时，怎样控制远程读的发起，使容量扩展真正改善推理完成时间？** 先检验这个问题是否在真实轨迹中成立，再决定实现机制。原来的“服务能力感知内存池”仍可作动机，但单独作为贡献太宽。

## 1. 这些工作已经把什么做了

不能只按 Host、CXL、Ethernet 分组。更关键的是：存什么、何时读取、在哪里计算，以及主要减少哪一段时间。

| 路线 | 代表工作 | 已覆盖的主要问题 | 对我们的约束 |
| --- | --- | --- | --- |
| Host 容量扩展与数据搬运 | FlexGen、InfiniGen、HeadInfer | 分层放置、批处理流水、选择性 KV 预取、按 head 卸载 | “把 KV 放到便宜内存”不足以成贡献；选择性读取必须固定算法与精度 |
| CPU–GPU 协同计算 | FastDecode、NEO、FlexInfer、LIA | 把 attention 等计算放到 CPU，联合调度计算与数据传输 | 不能只比较链路带宽：CPU 计算能力和开销也属于资源预算 |
| MoE 权重卸载 | PowerInfer、MoE-Infinity、MoE-Lightning、Fiddler | 稀疏性、专家缓存/预取、CPU 专家执行、GPU–CPU–I/O 流水 | 每步重读全部所需远程专家不是天然合理的强基线 |
| CXL KV 与缓存池 | Beluga、TraCT、LLM KV Cache Storage Using CXL Memory、Adaptive CXL KV Scheduling | GPU 访问路径、KV 转移、前缀复用、分层缓存与调度 | “CXL/MPU 能存 KV”“改善 TTFT”已有工作；要区分缓存恢复与活跃 decode 访问 |
| 高带宽 CPU 内存 | SuperInfer | NVLink-C2C 上的请求轮换、SLO 调度、KV 双向搬运 | “带宽大仍然有阻塞”“调度扩大可服务容量”也不是空白 |
| 网络内存池 | Mooncake、MemServe、CMM-MP、EMFASYS | 分布式 KV 管理、缓存局部性、独立内存设备与 Ethernet 数据路径 | 仅增加独立内存节点或 Ethernet 接口不够新；产品页不能代替论文实验 |
| 计算随内存分布 | Infinite-LLM、Lamina、CENT、PNM KV | 分布式 attention、近存计算/筛选 | 与纯存储 MPU 是不同架构；不能把减少回传量的收益全部算成网络优势 |
| 放置与建模 | Dynamic KV Placement、CXL Pool Simulator、Evaluating CXL Pooling | 容量/带宽优化空间、共享权重池、校准仿真与解析比较 | 通用放置优化式或“支持 CXL 的仿真器”已经不够 |

表中链接、正式标题与出版状态见 [逐篇索引](ref/README.md)。LIA、Adaptive CXL KV、CXL Pool Simulator、Evaluating CXL Pooling 未取得全文；对这四篇的判断只到公开摘要层面，不推断它们没实现某项功能。

### 最影响选题的六个发现

1. **CMM-MP 与我们的设备形态非常接近。** 它通过本地主机 CXL 接口连接后端 Ethernet 内存池，正文已有请求 tag、地址映射、CXL 信用与背压、在途事务表及重传。主应用评估包括 Valkey 和 DiskANN。因此“我们把请求变成 Ethernet 包，并正确返回”是实现基础，不是独立研究贡献。[原文](https://arxiv.org/abs/2610.22716)，[本地 PDF](ref/papers/cmm-mp.pdf)，PDF 第 4–6 页。
2. **其配套 CXL KV 论文已经做真实 LLM 框架评估。** 使用 vLLM 与 LMCache 比较不同 offload target，包含 CMM-MP。冷热缓存、查找、取回、prefill 与 decode 的区别是理解结果的关键，不能把缓存命中带来的 TTFT 改善解释成每个 decode step 都在远端扫 KV。[出版记录](https://doi.org/10.1109/LCA.2026.3720952)，[本地 PDF](ref/papers/cxl-kv-storage.pdf)，第 1、3–4 页。
3. **SuperInfer 已经讨论高带宽互连下的服务调度。** 论文针对 GH200 的 NVLink-C2C、KV 轮换和传输引擎；正文分析 DRAM 与双向搬运限制。它不是多 XPU 共享交换网络的独立 MPU，但已覆盖“带宽提升不等于消除阻塞”的宽泛论点。[原文](https://arxiv.org/abs/2601.20309)，[本地 PDF](ref/papers/superinfer.pdf)，第 3–5 页。
4. **TraCT、Beluga 让“GPU 直接访问 CXL 池”也不能独占。** TraCT 的主要语义是 P/D 之间的 KV 交换和机架级前缀缓存；Beluga 研究 GPU 访问 CXL 池与 KV 管理。必须画清实际访问路径，DMA 经主机/root complex 的访问不等于 GPU 原生发出 CXL.mem。[TraCT](https://arxiv.org/abs/2512.18194)、[Beluga](https://arxiv.org/abs/2511.20172)，本地 [TraCT PDF](ref/papers/tract.pdf)、[Beluga PDF](ref/papers/beluga.pdf)。
5. **动态 KV 放置已有非常接近的优化动机。** Dynamic KV Placement 在容量约束下研究异构内存带宽利用，并用未来访问知识估计放置潜力；这是设计空间上界，不应当作可在线部署策略。我们不能只把同类表达式中的 DRAM 改成 MPU。[原文](https://arxiv.org/abs/2508.13231)，[本地 PDF](ref/papers/dynamic-kv-placement.pdf)，第 1–2 页。
6. **经过硬件校准的池化推理仿真也已有先例。** CXL Pool Simulator 的公开摘要明确：共享池保存模型参数、KV 与激活保留本地，整合 LLMServingSim、ns-3 和 Mess，并以两台服务器连接真实池验证。它与我们访问语义不同，但提高了验证门槛。[作者机构摘要](https://pure.kaist.ac.kr/en/publications/a-simulator-for-llm-inference-systems-exploiting-cxl-memory-pools/)。本次未获取全文。

这些证据意味着：能做的方向仍然不少，但应落到**特定架构中的新失效原因及其修复**，而不是继续扩充“支持某种内存”的列表。

## 2. 推荐主线：远程读取何时应该暂缓发起

暂定题目：**When Memory and Collectives Share the Fabric: Completion-Aware Ethernet Memory Pooling for MoE Inference**。

中文：**当内存访问与集合通信共享网络：面向 MoE 推理完成时间的以太网内存池设计**。

要验证的现象是：相同工作集、相同请求字节量和相同硬件资源下，让 MPU 持续忙碌、尽快发出所有读取，可能延长应用阶段的完成时间。原因可能是返回流量提前占住共享链路或接收缓冲，而 GPU 当前所需的集合通信、短请求或 HBM 消费被延迟。这里“可能”必须由轨迹、队列时间分解和消融共同证实。

### 为什么比“MPU 带宽不足”更值得研究

一个远程读至少涉及三种不同生命周期：

- **内存服务槽位：**从 MPU 接纳到内存服务结束。
- **端到端读事务：**从发起到接收端完成所定义的接收/落地步骤。
- **链路信用：**对应具体链路缓冲及其返还条件。

内存服务结束不代表返回数据已被接收端消费。增加服务槽位可能只把积压转移到回程路径。另一方面，把所有请求窗口都压小又可能浪费内存与网络并行性。论文要解释的是这两个边界，以及它们怎样影响真正的依赖完成时间。

这是现有文献基础上的**候选切入点**，还不能声称首次发现。接收端调度、信用准入、两端瓶颈联合控制已有 [Homa](https://people.csail.mit.edu/alizadeh/papers/homa-sigcomm18.pdf)、[ExpressPass](https://people.csail.mit.edu/inhocho/papers/sigcomm17credit.pdf)、[SIRD](https://www.usenix.org/system/files/nsdi25-prasopoulos.pdf)。新意必须来自内存事务的返回承诺、接收侧消费约束和推理依赖之间的具体关系，且优于这些思想的合理基线，而不是换名字。

### 第一版只设计一个控制点

先做**面向返回数据接收能力的远程读准入**，固定放置、拼包与合法 VC 映射：

1. 发出读请求前，根据返回大小预留相应接收预算，并检查所需在途事务额度。
2. 分开记录 MPU 服务完成、返回到达、有限接收缓冲释放/HBM 落地等事件。预算必须在对应资源真实释放时返还，不能统一在内存服务结束时返还。
3. 在可发请求中，优先处理即将阻塞依赖消费者的读取；只使用运行时可获得的 DAG 就绪状态、等待年龄或有限预测，不使用未来真值。
4. 留出有界的公平服务份额。集合通信和返回流量也必须具有可证明的前进路径，不能依赖永不释放的循环资源。

第一项可构成无语义基线，第三项才是候选增益来源之一。逐跳信用解决物理缓冲安全，事务准入解决何时产生未来返回流量；二者不能混成一个“信用数”。粗粒度 hint 的传递、计数器/队列状态、更新延迟和实现代价都要计算。

先选静态窗口与简单接收反馈，若已经足够好，就不要强行引入动态预测。原提案里的联合放置 SAPA 暂时作为扩展，避免一篇论文同时优化放置、缓存、拼包、VC 和准入而无法归因。

### 最关键的反证实验

固定容量、有效请求、访问算法、链路、总缓冲和信用，扫描读窗口。画出：

- 横轴：实际允许的端到端在途返回量/请求数。
- 左纵轴：远程内存自身的吞吐与事务完成时间。
- 右纵轴：代表推理阶段完成时间及其中集合通信等待。

**希望检验而非预设的结果：**内存吞吐最优点与应用完成时间最优点是否分离。若存在，再看接收预算与依赖提示能否稳定接近后者。报告完整负载范围，包括无收益区和退化区，不挑单点。

还应比较相同字节量下的真实到达顺序与去相关到达顺序。若效应仅在人为同步突发中出现，真实轨迹不支持，就不应作为主线。独立网络仅作干扰消融；若多用了链路/端口，不能称等成本优胜方案。

## 3. 当前平台有两处决定性的前提缺口

**第一，不能默认活跃 KV 与 MoE 同时争用。** 当前 [行为手册 §3.3](../../docs/manual/03-behavior-model.md) 中，公共 KV/计算之后才是 TP AllReduce、dispatch、专家工作和 combine；每步还有全局完成屏障。一个同步代表块并不自然产生持续的 KV–MoE 重叠。

可研究的重叠来源包括不同请求或独立 DP 组异步推进、实际系统已有的预取，以及前缀恢复与 decode 并存。必须先取得真实事件时间线或可核验执行器轨迹；保留每个请求内部依赖。不能为了制造冲突把本来串行的操作任意改成并发。若主要问题是专家权重读取与 dispatch/combine 的关系，就收窄到该组合。

**第二，当前 MPU 槽位并非完整端到端背压。** [行为手册 §3.8–3.13](../../docs/manual/03-behavior-model.md) 描述的 MPU 服务结束后释放槽位，与返回网络及目的 HBM 消费并不等价。模型还需要补齐有限返回队列、目的接收缓冲和真实释放事件，才能判断上述机制。补齐正确性必须对所有方案同时生效；不能拿修复前的无限缓冲行为作弱基线，称为优化收益。

其他必要条件：限制端口/Die 聚合注入能力；区分交换流水线延迟与包启动间隔；校准队列/服务/信用参数；审计时间取整、IFG 与调度。当前 1 ps 时间分辨率只代表数值精度。

## 4. 如果主线不成立，还有两条较窄路线

| 方向 | 可研究的问题 | 与已有工作区分所需的证据 | 建议 |
| --- | --- | --- | --- |
| 稀疏访问的有效返回带宽 | 相同有用数据量下，页/事务/拼包/分片粒度怎样放大网络与接收开销；能否做受限 gather 或返回整形 | 固定同一 attention/查表选择结果与精度，使用真实地址、重复率和对齐；区别于 InfiniGen 的算法选择、TRACE 的表示压缩、PNM 的计算筛选 | 第二优先级；需要真实访问轨迹和明确 MPU 能力 |
| 在给定时间预算下真正可服务的池容量 | 活跃 KV、可复用前缀、专家缓存各应占多少本地容量和远端服务份额 | 与缓存/放置强基线比较；固定算力与 HBM，拆分容量扩展和服务能力扩展；不能只报装得下多少 | 适合作为主线的应用结果，单独成篇需要更强机制 |

不建议当前直接转向“MPU 执行 attention”。CENT、Lamina 与 PNM 系列已有不同实现；我们需要新的计算模型、指令/算子映射和校准。这会显著改变研究对象。若确有近存计算硬件，再另立题。

## 5. 最小证据链与继续/停止条件

### A. 先做可行性筛选

选择一个有来源的 MoE 工作负载，拿到请求/阶段时间、访问大小、目标与依赖；明确是活跃 KV 读取、前缀恢复还是专家读取。用少量代表条件检查真实重叠和资源瓶颈，不直接跑全矩阵。

将“内存只读负载”“通信单独运行”“两者真实交织”并列；分别扫描服务并发、端到端窗口、接收缓冲，控制其余资源。单独设置无重叠场景作为负例。若改变结论所需的参数没有硬件依据，应报告不确定区间。

### B. 基线要能排除平凡解释

| 基线/消融 | 目的 |
| --- | --- |
| 每场景调优的固定窗口、静态带宽 pacing | 排除只是默认参数太差 |
| 按类公平/优先级服务，含相同老化规则 | 排除只是让关键小流优先 |
| 仅接收字节预算、不使用依赖提示 | 判断应用语义是否真的有帮助 |
| 两端负载感知的通用准入策略 | 对照已有传输控制思想，不冒称完整复现其他协议 |
| 完整候选策略，以及逐项移除提示/消费反馈 | 解释收益来源与实现开销 |
| 可见未来的离线调度 | 仅作带有未来信息的参考，未经证明不能称严格最优上界 |

CPU attention、选择性 KV、量化、PNM 可以作为系统替代方案，但不能偷偷混入只改变传输机制的比较。CXL 与 Ethernet 对比必须画完整路径，匹配计算能力、容量和方向性带宽；不要给所有 CXL 配置套一个固定延迟。

### C. 指标与容量口径

当前平台优先报告代表阶段完成时间、关键依赖等待分解、有用字节/线上字节、实际信用阻塞时长、各类队列占用、端到端在途量与公平性。p99 需要足够样本和独立重复；没有完整在线服务执行器，不能把代表窗口时间命名成完整模型 TPOT/TTFT 或线上 SLO 吞吐。

容量实验必须真的触及容量边界。[现有实验边界 §9.7](../../docs/manual/09-mpu-pcie-offload.md) 的审计表明，已有几个 offload 工作集都能装进一个 512 GB MPU，多 MPU 的加速不能直接解释为容量收益。需要分别控制总容量、总服务带宽、端口和服务槽位，或明确报告它们共同变化。成本/功耗比较要有可核验模型，不能随意给价格。

### D. 停止条件

若真实轨迹无相应重叠、效应仅来自时间取整/无限注入/错误资源释放，先修正模型；若收益落在校准误差或参数不确定性内，不宣称优势；若调优固定窗口与简单公平服务已匹配候选策略，就保留设计边界结论，放弃复杂控制器。

有说服力的最终三项贡献应当是：**在明确负载与架构边界内揭示一种可复现的失效机制；用经过分层校准的事务模型解释它；提出资源守恒、开销可实现且胜过强基线的修复。** 目前这三项都是目标，而不是已完成结果。

## 6. 阅读顺序

先读 CMM-MP、CXL KV Storage、SuperInfer，明确最近的架构与服务调度边界；再读 MoE-Lightning、NEO、Dynamic KV Placement，建立强基线；然后读 TraCT、Beluga、Mooncake 与 KVCache Cache in the Wild，确定缓存/恢复语义和真实局部性；最后对照 SIRD/Homa 检查准入机制是否只是已有方法的直接移植。其余文献用来扩展相关工作和界定适用范围。

本次只整理资料与研究方案，未新增仿真实验、修改协议实现或生成性能结论。论文工程里的英文初稿仍是上一版提案；后续选题收敛时应按本文重新组织，而不是将这里的假设直接写成实验结果。
