# MPU 可以讲什么故事

> 文献调研后的修订建议见 [RESEARCH_SYNTHESIS.md](RESEARCH_SYNTHESIS.md)。本文件保留初始提案；其中通用的容量/带宽感知放置不是已确认的新贡献。后续优先验证共享网络中的远程读准入问题，再决定是否保留联合放置 SAPA。

## 推荐主线：让内存池增加“可按时服务的容量”

**MPU 的价值不是让一次远程读取比 HBM 更快，而是在给定 XPU/HBM 资源下，让更多上下文和请求能够被及时服务。问题是：装得下的数据，不一定服务得过来。**

暂定题目：**Beyond Capacity: Service-Aware Memory Pooling for Ethernet Scale-Up Inference**。

论文要回答三个连贯问题：增加内存池什么时候能扩大可服务工作集；为什么容量和标称带宽充足时仍然失效；如何通过一项具体机制，把容量收益转化成及时完成的推理工作。

相对于另一条“拼包＋VC信用”路线，本篇的优化决策是**数据放在哪里、每个池接纳多少工作、释放多少远程事务**。拼包、信用、包率作为影响这些决策的底层机制和消融因素，第一版固定其策略，避免同时提出两套控制器。

## 1. 一个可以被推翻的中心假设

相同的远程数据容量，可能产生非常不同的服务需求：

- 活跃 KV：每个 decode 步读取多少，取决于注意力结构和实际访问；dense attention 的旧 KV 不能仅因“旧”就当作冷数据。
- 暂停会话/可复用前缀：主要消耗驻留容量，恢复时产生突发；“不用时驻留远端”和“每步远程读取”必须分开。
- 查表数据：可能以较低总字节量产生大量短事务；真实地址、对齐、热度和重复访问决定放大率。
- MoE：通信与远程内存共享网络资源；热专家权重若每步从池中读取，还会产生不同于 KV 的服务需求。

**待验证假设：**在容量受限、混合访问的场景中，按容量或标称带宽放置数据会高估可接纳负载；显式计入每个池的事务服务能力、每条共享路径和接收消费能力，能够扩大满足时间预算的负载范围。

不能只展示“多加 MPU 比少加 MPU 快”。增加节点通常同时增加容量、DRAM 带宽、网口和并发槽位，无法据此把收益归因于内存池架构或调度策略。

## 2. 架构解释：容量有存储上限，也有服务上限

对池 p，定义 C_p 为物理可用容量。数据类 j 在该池驻留 x_jp 字节；a_j 为每个指定服务周期需要读取的驻留数据比例，A_jp 为传输放大率（返回/写回/对齐分别核算），周期为 Δ 秒。平均服务需求示意为：

    D_p = Σ_j x_jp · a_j · A_jp / Δ       [byte/s]
    Σ_j x_jp ≤ C_p
    D_p ≤ B_p,useful

这只是固定工作集、明确访问语义下的必要条件，不是尾延迟保证。恢复突发、排队、相关到达和计算依赖必须通过时序验证；驻留热度与读流量不能都用同一个比例代替。读写分方向计算，需要相加的共享资源按其真实服务语义合并。

有效服务能力的诊断上界可以写成：

    B_p,useful ≤ min(B_memory, B_path, B_receiver,
                     N_service · g / L_service,
                     N_e2e · g / RTT_e2e,
                     P_path · u_packet)

各项统一换算为有效载荷 byte/s。g 是每个被计数事务的有效字节；u_packet 是平均每个包承载的有用字节；信用窗口需按实际计费单位及返还时间单独约束。这不是新的 roofline 理论，也不是完整网络的一个标量：多个池共享的端口/交换资源还要加**跨池约束**，不能给每个池复制整条链路带宽。

这里最容易混淆的两种并发：

1. N_service：MPU 内存准入至数据服务完成的槽位；占用时间 L_service 不含后续网络返回。
2. N_e2e：发起至响应被安全接收/消费的端点事务窗口；需要另行定义和实现，不能拿 MPU 的 128 槽位代替。

当前配置的一个**解析示例而非实验结果**：128 × 256 B / 200 ns = 163.84 GB/s，已经低于每 MPU 配置的 190 GB/s。实际槽位还经历数据服务和排队，所以这是宽松上界；不能把“约需149个槽位覆盖纯固定延迟”当作满带宽保证，更不能拿往返网络时间替换这里的200 ns后声称是现有实现的瓶颈。

对固定访问类别、固定服务预算和硬件，定义 **serviceable capacity（可服务容量）** 为满足该预算的最大驻留工作集。混合类别时报告可行域或 Pareto 曲线，不把所有数据压缩成一个普适 GB 数值。

## 3. 具体机制：服务预算约束下的放置与事务准入

第一版做离线配置器＋端点有限窗口，暂称 **Service-Aware Placement and Admission（SAPA）**。这只是工作名，未做名称唯一性检索，机制尚未实现。

输入：对象/分片大小、实际访问统计、阶段依赖、时间预算；每 Die HBM 余量；Host/MPU 容量；校准过的事务服务曲线；共享端口映射及 MoE 背景负载。不能只看全机 HBM 总量，必须检查每 Die 放置约束。

输出：对象到 HBM/Host/MPU 的映射、MPU 分片方式，以及每类流量可用的端到端在途窗口。协议仍保持原端口返回、事务顺序及完成语义；准入 token 不冒充网络 VC credit。

可以先实现一个可解释的贪心版本：

1. 对每个可迁移对象，评估迁到各层后释放的 HBM 容量，以及新增内存字节、事务数、共享链路占用和关键路径延迟。
2. 在容量、阶段预算和各共享资源剩余额度内，选择可行的迁移；使用“释放 HBM / 主导资源新增压力”排序，分母为零的对象单独处理。目标是最大化可接纳工作集，不能通过少接纳请求制造低延迟优势。
3. 每次放置后重算共享路径需求；对热点进行分片，只在实际能分散服务队列、且额外包开销可接受时采用。第一版不复制数据，避免引入一致性和额外容量混淆。
4. 在请求源端限制远程在途事务，并保留有限响应缓冲。响应额度只有在接收端定义的消费点完成后才释放；MPU 的内部服务槽位保持独立生命周期。
5. 对同一 trace 做因果回放，若发生服务预算违约则回退到本地、Host 路径或拒绝新增工作。拒绝数量和未服务工作量必须计入结果。

静态窗口也需要公平调度/有界等待，读响应所需资源不能被新请求无限占用。涉及新返回保留机制时，明确缓冲预留、错误清理和前进条件并验证；不能把缩小窗口当成天然无死锁证明。

小规模穷举最佳静态配置作为经验上界。训练 trace/微基准用于估计服务曲线，未见过的到达、局部性和访问分布用于验证，避免把逐案例调参包装成在线算法。若静态版本无收益，不优先叠加动态控制。

## 4. 和已有工作的边界

以下为本次原始来源检索，不是完整相关工作综述：

| 工作 | 已有重点 | 对本篇的约束 |
|---|---|---|
| [Mooncake](https://arxiv.org/abs/2407.00079) | KV 池、prefill/decode 分离、SLO 调度、预测性提前拒绝 | “内存池＋SLO＋准入”已经存在；必须具体说明端点事务与共享服务资源怎样改变决策 |
| [MemServe](https://arxiv.org/abs/2406.17565) | 弹性内存池、上下文缓存、全局局部性调度 | 不能把热冷分层、前缀复用或统一池化本身当贡献 |
| [Dynamic KV Cache Placement](https://research.ibm.com/publications/accelerating-llm-inference-via-dynamic-kv-cache-placement-in-heterogeneous-memory-system) | 容量约束下异构内存 KV 放置与带宽利用的理论上界 | “容量＋带宽的优化公式”不够；需要真实事务和队列导致的设计差异 |

候选新增文献还包括 [Evaluating CXL Memory Pooling for Scalable LLM Inference](https://ieeexplore.ieee.org/abstract/document/11459268) 和 [CXL 内存池推理仿真器](https://pure.kaist.ac.kr/en/publications/a-simulator-for-llm-inference-systems-exploiting-cxl-memory-pools/)。前者此次原文获取失败，后者只检索到机构摘要；均需要后续阅读全文，不能据摘要断言其缺少某项能力。

可争取的差异是：**在 Ethernet MPU 上，将内存槽位、发起窗口、有限响应缓冲、共享 fabric 和 HBM 消费约束共同转化为放置/准入决策，并用校准证据验证其必要性。** 这是研究方向，不是已证明的新颖性。

## 5. 当前仓库能支撑什么

本节基于仓库手册与配置，不是一次全源码正确性审计。

| 能力/证据 | 现状与用途 |
|---|---|
| 完整模型容量预算＋代表块 DAG | 可以先找容量边界、研究代表窗口；不能直接报告整模型 TPOT/TTFT |
| MPU 逐256 B AXI服务、128槽位、190 GB/s | 可以扫描固定延迟、服务并发与带宽的拐点；配置值未经硬件校准 |
| AXI拼包、CBFC/LLR、共享HBM、事务级PCIe | 提供路径竞争和卸载基线；不能等同全链路缓冲闭环 |
| MPU内存服务结束即释放槽位 | 不是端到端窗口；等待准入及待返回数据的有限性需要补全 |
| SUE返回整消息收齐后写HBM | 缺少逐包接收消费与信用耦合，不能公平宣称其背压行为优于PCIe |
| 当前卸载比率 | 主要是Host/MPU分流；任意对象HBM驻留、在线迁移和连续batch不是现成功能 |
| 每任务1 ns注入 | 不等于每端口/Die的聚合发起能力，需要显式上限 |
| 交换机包率统计 | 不等于包处理吞吐上限；若主张受包率制约，需要流水线启动间隔/并行度模型 |
| 合成路由与地址 | 可用于机制测试；Engram聚合后拆AXI不能当真实逐行gather trace |
| 现有第9章330例结果 | 文档记录的历史实验；本次未复核原始记录，不能作为本篇新机制的实验结果 |

尤其是第9章明确指出：该轮所有卸载数据集小于单个512 GB MPU。那些结果主要展示增加服务资源的效果，**尚不能支撑“容量不足时内存池增加可服务请求”的中心主张**。需要新增跨越本地容量边界的工作负载，并允许 HBM-only 用更小 batch/排队服务，而不是把它的不可行大 batch 画成无限时延。

## 6. 实验按证据链推进

| 阶段 | 设计 | 要回答的问题 |
|---|---|---|
| A 校准 | 单MPU：事务大小、并发、读写比例；端到端：RTT、接收消费、返回缓冲；训练/验证分离 | 服务曲线和有限缓冲是否可信？ |
| B 机制 | 固定容量/带宽，独立扫描服务槽位、端点窗口、热点与共享路径；分别观察小事务与恢复突发 | 哪个约束造成“容量闲置但服务饱和”？ |
| C 方案比较 | HBM-only可行batch、Host PCIe、全MPU、均匀分片、容量优先、带宽比例、热度优先、SAPA、小规模静态oracle | 策略是否优于合理的已有启发式？ |
| D 消融 | 容量/带宽模型 → 加服务并发 → 加端到端窗口/有限缓冲 → 完整路径；SAPA分别去掉放置或准入 | 收益来自哪一项？简化模型是否选错？ |
| E 泛化 | 未参与选参的访问trace、batch、context、热点程度、MoE强度 | 能否跨场景成立，而非只对一个合成案例有效？ |

所有策略比较固定 XPU 数、每 Die HBM、远程总容量、带宽、端口、总槽位/缓冲/信用预算和计算负载。允许策略重新分配资源，但必须守恒。节点数扩展单独作为硬件扩展实验，报告新增资源，不能混为等资源策略收益。

第一轮只做诊断：选一个已支持模型，校验容量后，在同一小工作负载下比较2个服务并发值×2个共享流量强度，共4个条件；确认统计能解释后再扩展。新配置放 `configs/experiments/`，结果放新的 `results/sue/` 目录。该建议尚未生成配置或执行，以免研究提案自动变成昂贵矩阵。

当前可报告：阶段完成时间、任务/事务尾延迟、有效/线上字节、槽位占用、真实等待、容量准入与时间预算可行域。不能将多请求累计等待相加成关键路径。

最终应用指标：在同一外部到达流下，满足 TTFT/TPOT 约束的请求 goodput、拒绝率和可支撑上下文/并发数。需要先补真实逐层依赖、attention读写、到达与continuous batching；不能把代表块时间乘层数，也不能用少量合成任务的P99充当服务P99。无校准价格/功耗时，仅给资源开销表与参数敏感性，不给节省成本百分比。

## 7. 最值得做的图

**主图：物理容量与可服务容量之间的距离。** 横轴上下文或驻留工作集，纵轴可接纳并发；分别画容量上界、带宽模型预测、完整模型、SAPA。固定预算下标出容量不足、服务不足、可行三个区域。每个预测点都需明确依据；实际系统验证只覆盖可获得硬件的范围。

第二张是设计翻转：A按标称带宽把更多工作放入池，B按服务曲线保留/分流关键工作。两者硬件完全相同，简化模型选A、详细模型选B；用未参与校准的微基准或RTL验证关键瓶颈。**翻转是待寻找现象，不是硬性必须做出来的结论**；若不存在，应报告模型一致区间。

第三张是资源时间线：新请求受限 → 等待内存槽位 → 返回排队 → HBM消费 → 端到端额度释放。把服务槽位与端到端窗口分两行，防止读者误以为128槽位覆盖全过程。

## 8. 论文结构与停止条件

预期贡献收敛为三项：

1. 在明确负载和时间预算下量化以太网内存池的可服务容量边界，并解释容量、事务并发与共享资源的关系。
2. 提出可执行的放置/事务准入机制，报告控制状态、实现开销和前进条件。
3. 以分层校准和独立验证，证明何时该机制改善可服务负载，何时没有收益。

正文可按动机1页、背景与边界1页、机制3页、模型和校准2页、评估3页、相关工作与局限1页组织；是否能达到这一篇幅取决于实际证据，不以填满11页为目标。

停止/改题条件：若真实负载只受带宽控制、简单带宽比例启发式已足够，或所需背压结构与真实硬件不符，应降低架构机制主张；若无法获得关键子系统校准，只能写清假设下的仿真研究。不能靠人为缩小基线窗口、增加方案资源或数值取整缺陷制造优势。

**下一步最有价值的工作，是选定可获得校准数据的一条 MPU 请求—返回路径，完成有限缓冲闭环和四个小诊断案例，再决定是否投入完整论文。**
